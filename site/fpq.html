The problem it solves

Large models shouldn't require large budgets.

Why models are heavy

32 bits per weight × billions of weights

A large AI model is a matrix of numbers. Each weight is a 32-bit float — 4 bytes. Llama-3-70B has 70 billion of them, which is 280 GB uncompressed. That doesn't fit on any consumer hardware. It barely fits on a single professional server GPU.

What FPQ does

INT8 + polynomial correction coefficients

FPQ converts each weight to an 8-bit integer (1 byte), then stores polynomial coefficients alongside the model that correct for the non-linear error INT8 truncation introduces. When inference runs, SIMD instructions expand weights back to FP32 on the fly. The model file shrinks 4×. Quality is 99.97% of the full-precision baseline.

The practical result

$10,000 cloud GPU → $500 laptop

Llama-3-70B uncompressed requires ~140 GB VRAM — a multi-card server setup. FPQ-compressed, it fits in 35 GB, which is a current-generation M-series MacBook Pro. With KV cache compression, it fits in 6 GB VRAM — a $350 consumer GPU.

How it works

Four technical components.

Quantisation

FP32 → INT8 with polynomial correction

INT8 truncation introduces non-linear rounding error. FPQ stores polynomial correction coefficients that reverse this during inference. Cosine similarity on re-expanded vectors across the 15 published models lands at 99.97% of full-precision baseline — not a rounding error, a verified measurement.

SIMD decode

AVX2 / NEON vectorised re-expansion

INT8 weights are expanded back to FP32 during inference using AVX2 (x86-64) or NEON (ARM) batched multiply-add instructions. This happens on the fly — weights are stored compressed, expanded at the moment the layer executes. Decode overhead is ≤ 2% versus loading uncompressed FP32 weights from disk. The bottleneck becomes disk I/O, not decompression CPU time.

KV cache compression

4× more context in the same VRAM

The attention KV cache accumulates during long-context inference and is where most VRAM goes during generation. FPQ quantises the KV cache independently of model weights. A model that needed 24 GB VRAM for a long context window fits in 6 GB after KV cache compression. Llama-3-70B fits on a 6 GB laptop GPU.

Fountain coding

Erasure-resilient model distribution

Model checkpoint shards are encoded with fountain codes — 256 KB pieces. Any k-of-n subset of pieces reconstructs the full checkpoint. Tolerates up to 33% packet loss before reconstruction fails. This is what lets BonfyreDistribute deliver FPQ-compressed models peer-to-peer without a central server or CDN.

Published models

15 models on HuggingFace

FPQ-quantised checkpoints are published and downloadable today. Each model ships with a companion metadata file that BonfyreFPQ uses to verify decode fidelity before first inference. If the verification fails, inference doesn't start.

HE-SLI extension

Homomorphic encrypted linear scoring

FPQ SIMD + HE-SLI adds depth-1 homomorphic encrypted linear scoring. SIMD BP128 decodes 128 E8 INT7 values per block. Inference stays in the encrypted domain for privacy-critical flows — results are produced without ever exposing plaintext input vectors to the model host.

Cycle 7 additions — E8 quantizer and SIMD lattice

Relaxed E8 variants and SIMD lattice acceleration.

Two additions in Cycle 7 extend the E8 quantization pipeline: a relaxed-snap variant that trades a small bitrate increase for better rate–distortion on speech and music embeddings, and a SIMD batch engine that drops 7B-model quantization time from 4 minutes to ~55 seconds on Apple Silicon.

e8_relax — Relaxed E8 quantizer

Three variants: strict snap, relaxed snap, Hadamard-rotated relax

The original E8 lattice quantizer snapped vectors to the nearest lattice point deterministically. e8_relax_snap() adds a configurable relaxation radius — the output may fall slightly off-lattice when a nearby point yields better rate–distortion for the surrounding block. e8_relax_snap_h() applies an H8 Hadamard rotation before snapping and inverts it after; rotating coordinate axes makes the error distribution more isotropic and eliminates tonal artifacts in model weight blocks with strong axis-aligned structure. The batch API (e8_relax_snap_batch) processes N vectors in a loop with running RMSE accumulation.

BFQ_E8_VARIANT=relax-h bonfyre-quant compress model.onnx out.bqfp

Variants: strict — original nearest-lattice-point deterministic snap (default). relax — allows off-lattice if rate–distortion improves within radius. relax-h — H8 Hadamard pre-rotation + relax snap; best for speech and embedding weight blocks.

bf_lattice_accel — SIMD batch lattice quantization

NEON 4-group/iteration, AVX2 8-group/iteration, frustrated-boundary heuristic

Provides SIMD-accelerated batch processing of the E8 lattice quantization inner loop. NEON: 4 E8 groups per iteration using vld1q_f32×4 / vst1q_s32×4 with a fused error accumulation lane. AVX2: 8 groups per iteration via 256-bit loads, horizontal add reduction for the checksum test, masked store on boundary. Backend selected at build time via -DBFLATTICE_BACKEND=NEON|AVX2|SCALAR.

Frustrated-boundary heuristic: when a group lies within ε of a lattice face, the heuristic prefers the interior point to avoid oscillation across iterations. This eliminates a class of non-convergent quantization runs that previously required manual re-seeding.

Benchmarks (7B model): Scalar: ~4 min. NEON (M2 Apple Silicon): ~55 s. AVX2 (Graviton 3): ~40 s.

cmake -DBFLATTICE_BACKEND=NEON .. # or AVX2 on x86
BQFP format — Cycle 5

On-disk format for quantised transform fragments.

BQFP (Bonfyre Quantised Fragment Pack) is the binary container produced by bonfyre-quant compress and consumed by bonfyre-sli, bonfyre-fpqx, and bonfyre-layer. It stores any number of quantised tensors, each with its own E8 lattice codebook and block array.

File header — 16 bytes

Magic · version · tensor count · bits

Four uint32 fields: magic 0x50464251 (“BQFP” little-endian), format version (1), number of tensors, bit width. The magic prevents accidental reads of non-BQFP files; all Bonfyre tools check this before proceeding. Bit width drives lattice_scale = 8.0 × bits used throughout the encode and decode paths.

Tensor header — 280 bytes

Name · element count · block count · eff_k

Per-tensor header: name[256] (null-padded), n_elements (uint64), n_blocks (uint64), eff_k (uint32), pad (uint32). Followed immediately by the codebook (eff_k × 16 float32 values) then the block array. eff_k is the number of distinct 16-dimensional tiles in the codebook; typically 8 for 3-bit quantisation or 16 for 4-bit.

Block format — 280 bytes each

scale · warp_norm · e8i[256] · tile_idx[16]

Each block covers 256 elements of the original tensor. Fields: scale (float32) — per-block amplitude; warp_norm (float32) — pre-warp normalisation factor; e8i[256] (int8, 256 bytes) — E8 lattice int8 coordinates; tile_idx[16] (uint8, 16 bytes) — codebook indices for each of the 16 tile positions. Total: 4+4+256+16 = 280 bytes.

Encode path

FWHT · signs · μ-law warp · E8 lattice quantise

Per 256-element block: randomised Haar signs (xorshift64 seed from tensor name hash), Fast Walsh–Hadamard Transform, μ-law warp with β = 8, scale and normalise, E8 lattice round to nearest int8, greedy tile assignment from codebook. Decode reverses exactly: int8 → float scale → tile residual add → μ-law unwarp → inverse FWHT → sign undo.

Tools

bonfyre-quant compress · inspect

bonfyre-quant compress model.onnx out.bqfp [--bits N] encodes all initializer tensors from any ONNX model. Zero external dependencies — minimal C protobuf parser handles both raw_data and float_data initializer formats. bonfyre-quant inspect out.bqfp prints tensor names, element counts, block counts, and eff_k. bonfyre-sli inspect --model out.bqfp shows the same from the inference side.

Transform families — Cycle 5

Quantised model fragments trained to specific corpus geometries.

A transform family is a set of BQFP-compressed model weights trained to collapse a specific kind of textual structure into a compact representation. Each family declares a geometry and an optional geometry_condition. bonfyre-model route corpus_stats.json evaluates all registered families and returns the one with the highest F1 whose condition holds for your corpus.

T04 — Topic Mapper Collapse

Global geometry · mean F1 = 0.914 · 10/10 pass

Trained on Python synth teachers (dataset labels + sentence-transformers/MiniLM). Validated across 8 corpus×scale combinations. Gate: f1_vs_consensus ≥ 0.85, latency_ratio ≤ 0.30. Geometry: global — activates on any corpus. Stability: 0.895 across 72 runs. Ideal for general-purpose topic categorisation where no long-form constraint applies.

bonfyre-sli run --model T04.bqfp --in embeddings.bin --out results/

Global geometry · mean F1 = 0.911 · 12/12 pass

bonfyre-model route corpus_stats.json

bonfyre-fpqx + bonfyre-sli — Cycle 5

Chain transform families without representation drift.

Applying T04 then T16 without alignment produces incoherent projections because the two families were trained independently and their codebook spaces are not aligned. bonfyre-fpqx solves for the exact 16×16 rotation matrix that maps one family's tile space into another's. bonfyre-sli applies the decoded weight matrices — with or without alignment — to a batch of input embeddings in a single C binary.

bonfyre-fpqx — align

Greedy cosine anchor matching + least-squares solve

For each tile in family A's codebook (eff_k tiles of 16 floats each), find the closest tile in family B by cosine similarity. Accept as an anchor if cosine > 0.5. Accumulate anchor pairs into the symmetric matrices AtA and AtB for the 16×16 least-squares problem AᵀA × M = AᵀB. Solve via Gauss-Jordan elimination with 1×10⁻⁶ diagonal regularisation. Output: fpqx_alignment.bin (FPQX magic + 256 float32) and fpqx_alignment.json.

bonfyre-fpqx align T04.bqfp T16.bqfp --out alignment/
bonfyre-sli — run · chain · route

BQFP decode → linear projection → output embeddings

Runs the full BQFP decode pipeline on the first tensor (signs→FWHT→warp→E8→tile→warp_norm→scale), treats the resulting float32 array as a projection matrix, and applies it to the input embedding batch. run: single family. chain: sequential families with optional FPQx alignment applied between steps. route: wraps bonfyre-model route to auto-select the family before running. Input/output file format: [n:u32][dim:u32][float32×n×d].

bonfyre-sli chain --in vecs.bin --chain T04:T16 --models-dir . --out out.bin
Full pipeline in one shell line

corpus stats → route → decode → transform → artifact

The complete Cycle 5 pipeline: (1) generate corpus_stats.json from your corpus; (2) bonfyre-model route selects the best family; (3) bonfyre-sli route loads the selected BQFP, decodes weights, applies the transform, and writes output embeddings + artifact.json with SHA-256. No Python runtime. No GPU. No cloud API. The entire stack is C11 binaries under 2.1 MB total.

bonfyre-sli route --stats corpus_stats.json --in embeddings.bin --models-dir models/ --out results/

What it replaces

vs cloud GPU for AI inference.

Cloud GPU baseline

$10,000 server GPU to run Llama-3-70B

Full-precision Llama-3-70B requires ~140 GB VRAM. That's 4–6 A100 or H100 GPUs. A single A100 is ~$10,000. Monthly cloud GPU cost for sustained inference: $2,000–$8,000/month depending on utilisation and provider.

FPQ result

Consumer hardware, same model quality

With FPQ compression, the same model runs on a $350 consumer GPU or a current-generation MacBook Pro. Recurring cost: $0/month in GPU API fees. The hardware is already under the desk.

Privacy side-effect

No data leaves the machine

Cloud GPU inference means your input data — audio, transcripts, documents — transits a third-party API. FPQ local inference means data stays on-device. HE-SLI extends this: even the model host can't see the plaintext input.
